## 1. 개요

Pan/Tilt 축 이동에 **사다리꼴 속도 프로파일(가감속 램프)** 을 도입한 내용을 정리한
문서입니다.

**문제.** 도입 이전에는 타이머 주기가 고정이라 축이 **정지 → 순항 속도**로 한 펄스 만에
튀어 올랐다가, 목표에 닿는 순간 똑같이 뚝 멈췄습니다. 스텝모터는 속도를 계단 형태로
바꾸면 로터가 고유진동으로 링잉(ringing)하며, 이 진동이 가라앉기를 기다리느라 스캔
시퀀서가 줄마다 정착 시간을 쓰게 됩니다. 방향이 뒤집히는 순간에는 탈조로도 이어집니다.

**해결.** 타이머의 ARR(자동 재로드 값)을 **펄스마다 다시 써서** 시작과 끝은 느리게,
가운데는 순항하도록 속도를 연속적으로 바꿉니다.

> **핵심 불변식: 이동 각도는 하나도 바뀌지 않습니다.**
> 램프가 건드리는 것은 **펄스 사이의 간격**뿐이고 **펄스 개수는 그대로**입니다. 따라서
> 목표 각도 · 좌표계 · 엔코더 대조 로직은 이 변경의 영향을 받지 않습니다. 회귀 검증
> 범위를 "소리와 시간"으로 한정할 수 있는 근거가 이것입니다.

### 1.1 설계 의도

이 변경으로 **얻으려던 것**과, 의도적으로 **건드리지 않기로 한 것**을 먼저 못박습니다.
이후의 모든 선택은 이 표에서 파생됩니다.

| 구분 | 내용 | 그렇게 정한 이유 |
|---|---|---|
| 얻으려는 것 | 출발·도착 시점의 **속도 계단 제거** | 링잉의 원인은 평균 속도가 아니라 **속도의 불연속**입니다. 순항 속도를 낮추는 것으로는 해결되지 않고 스캔 시간만 늘어납니다 |
| 얻으려는 것 | 반전 시 **탈조 방지** | serpentine 스윕은 줄마다 방향이 뒤집힙니다. 순항 속도에서 방향만 바꾸면 그 자리에서 탈조합니다 |
| 건드리지 않는 것 | **펄스 개수 = 이동 각도** | 각도가 바뀌면 좌표계 · 엔코더 대조 · 이미 찍은 스캔의 해석이 전부 흔들립니다. 램프는 "언제 펄스를 낼지"만 바꾸고 "몇 개를 낼지"는 바꾸지 않습니다 |
| 건드리지 않는 것 | **순항 속도** | 순항 속도는 라이다 샘플 밀도에 맞춰 이미 결정돼 있는 값입니다(8절). 램프는 이 값을 **주어진 입력으로 받고**, 종전 고정 속도를 그대로 순항 속도로 씁니다 |
| 건드리지 않는 것 | **기존 축 드라이버** | 펄스 발생 · 방향 출력 · 좌표 카운터는 이미 동작하는 코드입니다. 램프는 그 위에 **간격 결정만 얹는** 형태여야 회귀 위험이 없습니다 |
| 건드리지 않는 것 | **ISR의 단순함** | ISR에 상태머신이 들어오면 계층 분리로 없앤 부류의 버그가 되돌아옵니다. 그래서 램프는 분기 세 개와 나눗셈 두 번으로 끝나는 형태여야 했습니다 |

### 1.2 문서 범위

본 문서가 다루는 것은 **속도 프로파일 계층**입니다.

| 다룸 | 함수 / 상수 |
|---|---|
| 속도 → 타이머 반영 | `axis_set_speed()` |
| 감속 전환 판정 | `axis_decel_pulses()` |
| 램프 본체 | `axis_ramp()` |
| 타이머 시간축 확정 | `axis_timer_init()` |
| ISR 삽입점 3곳 | 반전 시 속도 되감기 · `remaining` 계산 후 `axis_ramp()` · 정지 중 되감기 |
| 램프 상수 | `MOTOR_START_PPS`, `MOTOR_*_ACCEL_PPS2`, `MOTOR_TIM_TICK_HZ`, 관련 `_Static_assert` |

**다루지 않는 것** — 축 드라이버 본체(팀원 구현). 펄스 발생과 STEP/DIR/EN 출력, 펄스 폭과
DIR 셋업 타이밍, `s_armed` 전류 게이트, 좌표 카운터와 엔코더 · 영점 · I2C, 그리고 **순항
속도 값 자체의 선정**이 여기 해당합니다. 램프는 이들을 전제로 얹힌 계층이며, 아래 2절이
그 전제 중 램프가 의존하는 부분만 요약합니다.

## 2. 전제 — 램프가 올라탄 토대

기존 축 드라이버에서 램프가 의존하는 성질은 세 가지뿐입니다.

| 전제 | 내용 |
|---|---|
| 펄스 생성 방식 | 타이머 Base 인터럽트 1회당 **최대 1펄스** (TIM1=Pan, TIM2=Tilt) |
| 따라서 | **타이머 주파수 = 그 순간의 pps** → **속도 제어 = ARR 제어** |
| 분해능 | 1.8° / 16 마이크로스텝 = **0.1125°/펄스** (= 1.125 ddeg) |

두 번째 줄이 램프가 가능한 이유 전부입니다. 펄스를 하나 낼 때마다 "다음 펄스까지
얼마나 기다릴지"를 다시 계산해 ARR에 실으면, 그것이 곧 속도 프로파일이 됩니다.

TIM1이 **16비트** 타이머라는 점만 별도 제약으로 작용합니다(5절).

## 3. 속도 프로파일

```
   pps
    ^      ______________________ cruise
    |     /                      \
    |    /                        \
start ──/                          \──
    +--------------------------------------> 남은 펄스
```

전이 규칙은 네 가지입니다.

| 상황 | 동작 |
|---|---|
| 정지 상태에서 출발 | 언제나 `MOTOR_START_PPS`(50pps)에서 시작 |
| 가속 구간 | 매 펄스 `accel × 펄스간격` 만큼 속도를 올리고, 순항 속도에서 클램프 |
| 감속 전환 | **"지금 속도에서 시작 속도까지 감속하는 데 필요한 펄스 수" ≥ 남은 펄스 수** 가 되는 순간부터 감속 |
| 도착 / 정지 중 | 속도를 시작 속도로 **되감아 둡니다** — 안 하면 다음 이동이 직전 순항 속도로 급출발합니다 |

### 3.1 왜 이 방식인가 — 검토한 대안과 기각 근거

프로파일의 모양보다 **토대가 선택지를 먼저 좁혔습니다.**

**ISR은 램프와 무관하게 펄스마다 이미 돕니다.** `axis_step()` 이 STEP을 GPIO로 직접
올렸다 내리고(펄스 폭 4us 스핀), 위치 카운터 갱신과 DIR 반전도 같은 ISR 안입니다.
그 위에 얹는 나눗셈 두 번은 **펄스 폭 스핀보다 짧습니다.** 램프의 한계비용이 사실상
0이라는 뜻이고, 이것이 "매 펄스 다시 계산한다"를 정당화하는 근거입니다.

| 대안 | 기각 근거 |
|---|---|
| **타이머 DMA 버스트로 ARR 갱신**(DMAR/DMAB) | ISR 없이 프로파일을 돌릴 수 있지만, 그러려면 STEP을 PWM 출력으로 바꿔야 하고 위치 카운팅을 어디서 할지가 새 문제가 됩니다. 램프를 위해 **이미 동작하는 펄스 생성을 뜯는 것**은 §1.1의 "기존 축 드라이버를 건드리지 않는다"와 정면으로 어긋납니다 |
| **Austin 재귀식**(AVR446) — 스텝모터 램프의 표준 레퍼런스 | 나눗셈 한 번으로 되지만 상태로 **펄스 인덱스 `n`** 을 듭니다. 이 구현은 `v_q8`(현재 속도)을 직접 들기 때문에 이동 중 반전이 `axis_set_speed(ax, MOTOR_V_START_Q8)` **한 줄**로 끝납니다. `n` 을 들면 반전·목표 변경마다 `n` 을 역산해야 합니다 |
| **프리컴퓨트 램프 테이블** | 목표가 이동 중에 바뀝니다(§3.2) |
| **램프 제너레이터 내장 드라이버**(TMC5160 등) | 부품 선정 시점에 닫힌 선택지입니다. DRV8825는 STEP/DIR만 받는 단순 드라이버이고, 마이크로스텝도 물리 DIP 스위치로 1/16 고정입니다 |
| **순항 속도 인하 / 정착 지연 연장** | §1.1 참조. 전자는 링잉의 원인이 아니라 스캔 시간만 늘리고, 후자가 램프 도입 이전 상태입니다 |
| **S-커브**(저크 제한) | `v'` 의 불연속까지 없애지만 ISR 상태가 늘어납니다. 목적은 **출발·도착의 속도 계단 제거**이고 그것은 등가속으로 충족됩니다. 추가 이득의 크기는 이 부하에서 실측 없이 알 수 없습니다 |

**등가속이라는 가정 자체는 남아 있는 여지입니다.** 등가속은 "가용 토크가 속도와
무관하게 일정하다"를 전제하는데, 스텝모터의 pull-out 토크는 속도가 오를수록 떨어집니다.
즉 등가속은 저속에서 필요 이상으로 얌전하고 고속에서 낙관적입니다. 저속에서 더 세게
가속하는 프로파일이면 **같은 탈조 여유로 순항에 더 빨리** 도달합니다. 크기도 무시할
수준이 아닙니다 — 틸트 램프가 266펄스(29.9°)라 180° 스윕의 양끝 합쳐 **60°가 램프
구간**입니다(§8).

다만 이 논의는 **탈조 한계 실측이 선행되어야 합니다**(§10). 지금은 등가속의 여유가
얼마인지조차 모르는 상태라, 프로파일 모양을 바꿀 근거도 그대로 둘 근거도 없습니다.

### 3.2 왜 하필 그 지점에서 감속으로 돌아서는가

감속 전환 지점은 임의로 정한 값이 아니라 **제약을 만족하는 유일한 지점**입니다.

- **제약**: 목표에 닿는 마지막 펄스의 속도가 `MOTOR_START_PPS` 이하여야 합니다. 그래야
  도착이 "정지"와 연속입니다. 순항 속도로 목표에 닿으면 램프를 넣기 전과 똑같이 뚝
  멈추는 것이라 도입 목적이 사라집니다.
- **가능한 한 늦게**: 감속을 일찍 시작할수록 순항 구간이 줄어 이동이 느려집니다. 시간
  손해를 최소화하려면 제약을 깨지 않는 **가장 늦은 지점**이어야 합니다.

등가속도 운동에서 속도 `v` 에서 `v_start` 까지 내려오는 데 필요한 펄스 수는
`n = (v² − v_start²) / (2·accel)` 입니다. 따라서 "**남은 펄스 수가 `n` 이하로 떨어지는
순간**"이 위 두 조건을 동시에 만족하는 지점이고, 코드는 매 펄스 이 비교 하나만 합니다.

```c
if ((uint32_t)remaining <= axis_decel_pulses(v_pps, cfg->accel_pps2)) { /* 감속 */ }
```

**미리 계산해 두지 않고 매 펄스 다시 계산하는 이유**는 목표가 이동 중에 바뀔 수 있기
때문입니다(`motor_set_target` 은 메인루프가 언제든 부릅니다). 전환 지점을 이동 시작
시점에 한 번 굳혀 두면 목표가 바뀐 순간 그 값이 거짓이 됩니다. 매 펄스 계산은 나눗셈
한 번이라 굳혀 두는 이득이 없습니다.

**올림하는 이유**도 같은 제약에서 나옵니다. 내림하면 감속을 한 펄스 늦게 시작해 시작
속도보다 빠른 채로 목표에 닿습니다 — 제약 위반입니다. 올림하면 순항이 한 펄스 짧아질
뿐이므로, **틀릴 때 안전한 쪽으로 틀리도록** 올림을 택했습니다.

**짧은 이동은 삼각 프로파일이 됩니다.** 순항에 도달하기 전에 감속 전환 조건이 걸리기
때문입니다. 팬 격자 1스텝(0.9° = 8펄스)은 순항에 닿지 못하고 느리게 출발해 느리게
도착합니다 — **짧은 이동일수록 오히려 더 조용합니다.**

**이동 중 목표가 반대쪽으로 바뀌면** 속도를 시작 속도로 되감고 방향을 뒤집습니다.
감속은 로터가 못 따라올 수 없으므로(느려지는 것은 언제나 안전) 이번 펄스부터 즉시
적용해도 됩니다.

## 4. 램프 산수 — 전부 32비트 정수

ISR 안에서 매 펄스 도는 계산이라 **부동소수점을 쓰지 않습니다.**

**왜 고정소수점인가.** 속도를 pps 정수로 들면, 한 펄스당 속도 증가분(가속도 × 펄스간격)이
1pps 미만일 때 통째로 절삭되어 **램프가 그 자리에 얼어붙습니다.** 그래서 하위 8비트를
소수부로 쓰는 q8 고정소수점(`v_q8 = pps × 256`)으로 듭니다.

| 식 | 코드 |
|---|---|
| 펄스 간격 `c_us = 10⁶ × 256 / v_q8` | `c_us = MOTOR_C_NUM / v_q8` |
| 속도 증분 `dv_q8 = accel × c_us × 256 / 10⁶` | `dv_q8 = accel × c_us / MOTOR_DV_DIV` |
| 감속 소요 펄스 `n = (v² − v_start²) / (2·accel)` | `axis_decel_pulses()` — **올림** |
| ARR 반영 | `tim->ARR = c_us − 1` (속도가 실제로 바뀔 때만 씀) |

- `MOTOR_C_NUM = 2.56 × 10⁸` 으로 uint32 한도(4.29 × 10⁹) 안에 들어갑니다.
- `dv_q8` 이 절삭으로 0이 되면 **최소 1(=1/256 pps)** 로 보정합니다. 램프가 멈추는 것을
  막는 하한입니다.
- `MOTOR_DV_DIV = 10⁶/256 = 3906.25` 가 정수 나눗셈으로 3906이 되어 실효 가속도가 약
  **+0.006%** 높습니다. 램프 길이에 미치는 영향은 무시 가능한 수준입니다.
- 순항 중에는 속도가 변하지 않으므로 **ARR을 다시 쓰지 않습니다** — 불필요한 레지스터
  쓰기를 피하는 것이자, 프리로드 비활성 상태에서 같은 값을 덮어쓰는 위험을 줄입니다.

## 5. 타이머 시간축은 램프 계층이 직접 잡는다

`motor_init()` → `axis_timer_init()` 이 프리스케일러를 직접 설정해 **1틱 = 1us** 로
고정합니다. 그래서 ARR+1을 그대로 us로 읽을 수 있습니다.

```c
tim->PSC = (SystemCoreClock / MOTOR_TIM_TICK_HZ) - 1u;   /* 84MHz → 84-1 */
```

> **CubeMX가 `MX_TIMx_Init` 에 넣어 둔 Prescaler/Period 값은 쓰이지 않습니다.**
> 램프 계산이 "1틱 = 1us"를 전제로 하는데, `.ioc` 를 재생성하면서 그 값이 바뀌면 축
> 속도가 통째로 배수만큼 어긋납니다. 생성 코드가 무엇을 들고 있든 결과가 같도록 여기서
> 확정합니다. 반드시 `HAL_TIM_Base_Start_IT()` 보다 먼저 호출되어야 하며, 현 `main.c`
> 순서가 그렇습니다.

TIM1/TIM2 모두 타이머 클럭은 `SystemCoreClock`(84MHz)과 같습니다 — APB 프리스케일러가
1이면 그대로이고, 2 이상이면 타이머 쪽에서 2배 보상됩니다(현 클럭트리 APB1=/2, APB2=/1).

**PSC는 섀도 레지스터**라 업데이트 이벤트가 있어야 실립니다. `EGR=UG` 로 한 번 강제로
일으키고, 그때 선 UIF 플래그는 지웁니다 — 안 지우면 타이머를 시작하는 순간 밀린
인터럽트가 한 번 튑니다.

**ARR 프리로드는 비활성**이므로 쓰는 즉시 이번 주기에 반영됩니다. `axis_set_speed()` 는
ISR 진입 직후에만 불려 CNT가 수 us에 불과하고, 새 ARR은 최소 순항 간격 이상이라
**언제나 CNT보다 큽니다.** 만약 CNT보다 작은 값을 쓰면 카운터가 0xFFFF까지 돌아 그
주기만 통째로 길어집니다.

**16비트 ARR 한계는 컴파일타임에 막습니다.** 조용하게 만들겠다고 시작 속도를 무한정
낮추면 TIM1의 ARR을 넘습니다(하한 약 16pps).

```c
_Static_assert((MOTOR_TIM_TICK_HZ / MOTOR_START_PPS) <= 65536u, ...);
_Static_assert((MOTOR_START_PPS <= MOTOR_PAN_CRUISE_PPS)
            && (MOTOR_START_PPS <= MOTOR_TILT_CRUISE_PPS), ...);
```

두 번째 단언은 **순항 속도가 밖에서 바뀌는 값**이기 때문에 둡니다. 순항 속도가 시작
속도보다 낮아지면 프로파일이 성립하지 않는데, 그것을 런타임에 발견하고 싶지 않습니다.

## 6. ISR에 붙는 지점 (`axis_step`)

기존 ISR은 "전류가 있고 목표와 다르면 펄스 하나 내고 카운터를 증감"하는 코드였습니다.
램프는 여기에 **세 곳**을 얹습니다.

```
TIM1/TIM2 Base IRQ
   │
   ├─ 정지 상태(전류 없음 또는 도착)
   │       └─ ★ axis_ramp(ax, 0)         속도를 시작 속도로 되감고 종료
   │
   └─ 이동 필요                                    ┌ 기존 구현 ┐
           ├─ ★ 방향이 직전과 다르면 → 시작 속도로 되감기
           ├─ DIR 출력 → STEP 상승 → STEP 하강     │ (범위 밖) │
           ├─ pulse 카운터 ±1                      └──────────┘
           └─ ★ remaining 계산 후 axis_ramp()      다음 간격(ARR) 결정
```

**ISR 비용**은 나눗셈 두 번(Cortex-M4 UDIV 2~12사이클)이 전부입니다. 기존 ISR이 이미
쓰고 있던 펄스 폭 스핀보다 훨씬 짧으므로, 램프 도입으로 ISR이 길어져 라이다 UART
수신을 밀어내는 문제는 발생하지 않습니다.

### 6.1 왜 그 지점에서 그 일을 하는가

세 삽입점의 **위치**에는 각각 이유가 있습니다. 옮기면 조용히 깨집니다.

| 지점 | 왜 하필 거기인가 |
|---|---|
| 램프 계산이 **펄스를 낸 뒤**에 온다 | 계산하는 값이 "**다음** 펄스까지의 간격"이기 때문입니다. 펄스 전에 계산하면 이번 펄스가 이미 지난 간격으로 나가고, 판정에 쓰는 `remaining` 도 한 펄스 낡은 값이 됩니다 |
| 반전 되감기가 **DIR 출력 전**에 온다 | 되감기를 DIR 변경 뒤에 하면 그 한 펄스가 순항 속도로 반대 방향에 나갑니다. 탈조는 바로 그 한 펄스에서 납니다 |
| 되감기가 **도착 시점**에 일어난다 | 다음 이동의 첫 펄스는 정지 상태에서 나가므로 `START_PPS` 여야 합니다. 되감지 않으면 **다음 이동이 직전 이동의 순항 속도로 급출발**해 램프를 넣은 이유가 사라집니다 |
| 정지 중에도 **매 ISR이 되감기 경로를 지난다** | 즉시 정지(목표를 현재 위치로 당김)로 순항 중에 멈춰선 경우가 있습니다. 출발 시점에만 되감으면 그 경로를 놓치므로, 정지 중 상시 되감아 상태를 항상 정합하게 둡니다 |
| ARR 쓰기가 **ISR 진입 직후**에만 일어난다 | 5절 — CNT 추월을 구조적으로 불가능하게 만드는 유일한 타이밍입니다 |

## 7. 램프 파라미터

```c
#define MOTOR_START_PPS           50u    /* 양축 공통 출발/도착 속도 */
#define MOTOR_PAN_ACCEL_PPS2      600u
#define MOTOR_TILT_ACCEL_PPS2     1200u
```

순항 속도(`MOTOR_*_CRUISE_PPS`)는 **외부에서 주어지는 입력**이며, 아래 계산의 파라미터로만
쓰입니다.

램프가 잡아먹는 펄스 수는 `n = (v_cruise² − v_start²) / (2·accel)`, 소요 시간은
`(v_cruise − v_start) / accel` 입니다. 현재 값을 대입하면:

| 축 | 시작 → 순항 | 가속도 | 램프 펄스 | 램프 각도 | 램프 시간 |
|---|---|---|---|---|---|
| Pan | 50 → 100 pps | 600 pps/s | **7** | 0.79° | 0.083s |
| Tilt | 50 → 800 pps | 1200 pps/s | **266** | 29.9° | 0.625s |
| (참고) Tilt 400pps | 50 → 400 pps | 1200 pps/s | 66 | 7.4° | 0.292s |

비용은 **이동 양끝에서 한 번씩**입니다. 램프 도입에 따른 시간 증가는 이동 하나당
`2 × 램프시간 − 램프구간을 순항으로 갔을 때의 시간` 이며, 틸트 스윕 한 줄(180° =
1600펄스) 기준 순항 400pps에서 4.00s → 4.26s(**+6%**), 팬 180° 파킹은 16.00s → 16.06s로
사실상 그대로입니다.

### 7.1 왜 이 값인가 — 각 상수를 붙잡고 있는 제약

**`MOTOR_START_PPS = 50`** — 정지 상태에서 낼 수 있는 첫 펄스 속도(pull-in 영역).

- *아래에서 누르는 것*: TIM1의 16비트 ARR. 1틱=1us이므로 `10⁶/pps ≤ 65536`, 즉 **약
  16pps가 물리적 하한**입니다. `_Static_assert` 가 컴파일타임에 막습니다.
- *위에서 누르는 것*: 이 값이 곧 **출발·도착 시점의 속도 계단 크기**입니다. 높을수록
  램프를 넣은 효과가 줄어듭니다.
- *왜 50인가*: 하한(약 16pps)에서 3배 여유를 둔 값이며, **명시적 유도 근거는 남아 있지
  않습니다**(10절).
- *튜닝 시 참고*: 램프 비용은 시작 속도가 아니라 **순항 속도에 지배**됩니다.
  `n = (v² − v_start²)/(2a)` 에서 `v_start²` 항이 작기 때문입니다. 틸트를 50 → 16pps로
  낮춰도 램프는 266 → 267펄스(+1펄스, 시간 +28ms)에 그칩니다. 즉 **더 조용하게 만들고
  싶다면 시작 속도를 낮추는 것이 거의 공짜**이며, 실제 제약은 ARR 하한뿐입니다.
- 두 축이 같은 값을 쓰는 이유는 pull-in 속도가 순항 속도가 아니라 **모터·부하 자체의
  성질**이고 양축이 같은 모터이기 때문입니다.

**`MOTOR_*_ACCEL_PPS2 = 600 / 1200`** — 가속도.

- *위에서 누르는 것*: 모터 토크와 부하 관성. 너무 크면 로터가 못 따라와 **가속 중
  탈조**합니다. 이 한계는 계산이 아니라 실측으로만 확정됩니다.
- *아래에서 누르는 것*: 램프 길이 = 시간 손해. 작을수록 조용하지만 이동이 길어집니다.
- *왜 600 / 1200인가*: **유도 근거가 남아 있지 않습니다.** 결과로 나온 램프 비용(틸트
  한 줄 +6%)이 허용 범위였다는 사후 확인만 있습니다. 탈조 한계 대비 여유가 얼마인지는
  미확인이므로, **값을 올리려면 실측이 선행되어야 합니다**(10절).

## 8. 순항 속도와 라이다 — 경계 조건

순항 속도는 램프가 정하는 값이 아니라, **라이다 샘플 밀도에 맞춰 이미 결정된 값**을
받아 쓰는 것입니다. 관계식은 다음과 같습니다.

```
샘플 간격(도) = 틸트 각속도(도/s) / 라이다 레이트(Hz)
```

램프와 관련해 확인해야 할 것은 두 가지뿐입니다.

**① 램프는 샘플 밀도를 묽게 만들지 않습니다.** 펄스 개수가 그대로이므로 스윕 전체의
각도 커버리지가 같고, **가감속 구간은 순항보다 느리므로 오히려 샘플이 촘촘**해집니다.
즉 램프 도입으로 격자에 구멍이 생기는 방향의 변화는 원리상 일어나지 않습니다.

**② 램프는 빈 셀 진단에 단서를 줍니다.** 스윕 양끝은 램프 구간이라 샘플이 촘촘하고,
샘플 간격이 격자에 빠듯한 것은 **가운데 순항 구간**뿐입니다. 따라서 산출물에 빈 셀이
보일 때:

- 빈 셀이 **스윕 중앙**에 몰린다 → 순항 속도 대 라이다 레이트 문제
- 빈 셀이 **스윕 끝점**에 몰린다 → 램프 구간은 오히려 촘촘하므로 **다른 원인**

현재 값 기준으로 램프 구간은 스윕의 양끝 각 29.9°(합 60°)이고, 나머지 120°가 순항
구간입니다.

## 9. 한계 및 주의사항

**① 램프가 못 막는 것 — 즉시 정지.** `motor_disarm()` / `scan_stop()` 은 **목표를 현재
위치로 당기는** 방식이라 남은 펄스가 0이 되어 순항 속도에서 그대로 끊깁니다. 감속 전환
조건을 거칠 기회 자체가 없습니다. 중단 경로라 의도한 동작이며, 충격 수준은 램프 도입
이전과 같습니다. 부드러운 정지가 필요해지면 "목표를 당기는" 방식 대신 **감속 거리만큼
앞의 지점을 목표로 주는** 방식으로 바꿔야 합니다.

**② 램프 상태는 ISR 소유입니다.** `v_q8` / `c_us` / `forward_prev` 는 ISR만 읽고 씁니다
(`motor_init` 예외 — 타이머가 아직 안 돌 때). 그래서 `volatile` 도 락도 없습니다.
메인루프에 노출하지 않는 이유는 **펄스마다 바뀌어서 밖에서 본 순간 이미 낡은 값**이기
때문입니다. 진단이 필요하면 스냅샷 API를 별도로 만들어야 하며, 이 변수들을 직접 읽는
코드를 추가하지 마십시오.
