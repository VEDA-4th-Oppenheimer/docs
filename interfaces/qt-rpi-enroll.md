# Qt ↔ RPi 등록·발급 계약 (HTTPS 8443)

| 항목 | 내용 |
|---|---|
| 문서 ID | `ADTS-ENR-50` |
| 담당 | 송영빈 (Qt 클라이언트 · 발급 서버) / 이현우 (브로커 운영 · CA 스크립트) |
| 대상 소스 | `RPi/broker/enroll_service.c` · `QT/src/EnrollDialog` · `QT/src/ScanFetcher` |
| 기준 코드 | RPi `2a683ee` (2026-08-21) / QT `e777e73` (2026-08-21) |
| 경계 | Qt 관제 콘솔 ↔ RPi 발급 서비스 (`adts_enroll`) |
| 계약 버전 | v1.0 |

---

## 1. 개요

Qt 배포본에는 인증서도 카메라 설정도 담지 않는다. 인증서에는 `adts/cmd/#` 쓰기 권한이
있어 장비를 움직일 수 있고, 카메라 설정에는 카메라 admin 비밀번호가 RTSP URL 에 박혀
있다. 배포물에 넣으면 받은 사람 전원이 그 권한을 갖는다.

대신 사용자가 관리자에게 받은 **1회용 토큰**을 입력하면 이 서비스가 인증서·브로커
주소·카메라 설정을 한 번에 내려준다. 같은 서비스가 스캔 산출물(`.pcd`) 다운로드도
맡는다 — MQTT 로는 경로만 통지되고 파일 본문은 이 경로로 간다.

**이 계약을 바꾸면 양쪽이 같이 깨진다.** 서버는 `enroll_service.c`, 클라이언트는
`EnrollDialog`(등록)와 `ScanFetcher`(다운로드)다.

## 2. 엔드포인트

| 메서드 · 경로 | 용도 | 클라이언트 인증서 |
|---|---|---|
| `POST /enroll` | 인증서·설정 발급 | **불필요** |
| `GET /scans` | 스캔 파일 목록 | **필수 (검증된 것)** |
| `GET /scan/<파일명>` | 스캔 파일 본문 | **필수 (검증된 것)** |
| `GET /healthz` | 생존 확인 | 불필요 |

전부 **HTTPS 8443** 이다. 포트는 서버 환경변수 `ADTS_BIND_PORT` 로 바뀔 수 있으나 기본이
계약값이다.

## 3. TLS 요구사항

### 3.1 서버 → 클라이언트

- 최소 **TLS 1.2**
- 서버 인증서는 `<cert_dir>/server.crt` + `server.key`. **SAN 에 접속에 쓰는 IP 가 들어
  있어야 한다** — 클라이언트가 IP 로 붙기 때문이다.

### 3.2 클라이언트 → 서버

Qt 는 **실행파일에 내장한 `resources/ca.crt` 로만** 서버를 검증한다. 시스템 CA 는 쓰지
않는다. 발급 시점에는 아직 클라이언트 인증서가 없어 검증 근거가 이것뿐이다.

> `ca.crt` 는 **공개** 인증서라 배포본에 들어가도 안전하다. 다만 **CA 를 재발급하면
> 배포본도 같이 갱신**해야 한다. 안 하면 기존 배포본은 새 서버를 영영 신뢰하지 못한다.

### 3.3 서버의 클라이언트 검증이 두 단계인 이유

```c
SSL_CTX_set_verify(ctx, SSL_VERIFY_PEER, NULL);   /* FAIL_IF_NO_PEER_CERT 는 켜지 않는다 */
```

두 경로의 요구가 정반대다.

- `/enroll` 은 **인증서를 발급받기 전에** 부르는 곳이라 인증서를 요구할 수 없다.
- `/scan`·`/scans` 는 파일을 내주므로 검증된 인증서를 요구한다.

그래서 핸드셰이크는 누구나 되게 두고, **판정을 핸들러에서** 한다
(`SSL_get1_peer_certificate` + `SSL_get_verify_result == X509_V_OK`).

> 클라이언트 CA 를 서버가 못 읽으면 `/enroll` 은 그대로 뜨고 `/scan` 계열만 항상 401 이
> 된다. "발급은 되는데 스캔만 안 받아진다" 는 이 상태를 의심한다.

## 4. `POST /enroll`

### 4.1 요청

```
POST /enroll HTTP/1.1
Host: <RPi_IP>
Content-Type: application/json
Content-Length: <필수>

{"token": "3f9a1c…", "device_name": "youngbin-macbook"}
```

| 필드 | 필수 | 비고 |
|---|---|---|
| `token` | **예** | 빈 문자열이면 400 |
| `device_name` | 아니오 | 생략하면 `"-"`. 로그 식별용이며 CN 에는 안 들어간다 |

- `Content-Length` 헤더가 **없으면 400**이다. 청크 전송은 지원하지 않는다.
- 본문 상한 **8 KB**, 헤더 상한 **8 KB**.

### 4.2 응답 (200)

```json
{"cn":"qt-console-Youngbin",
 "ca_crt":"-----BEGIN CERTIFICATE-----\n…",
 "client_crt":"-----BEGIN CERTIFICATE-----\n…",
 "client_key":"-----BEGIN RSA PRIVATE KEY-----\n…",
 "mqtt":{"host":"172.20.32.110","port":8883},
 "cameras":{"channels":{"1":"rtsp://…","2":"…","3":"…","4":"…"}}}
```

| 필드 | 내용 |
|---|---|
| `cn` | **`qt-console-<라벨>`**. 라벨은 관리자가 토큰을 만들 때 정한 값 |
| `ca_crt` | 브로커 검증용 CA. 클라이언트가 저장해 MQTT 접속에 쓴다 |
| `client_crt` | 이 사람 전용 클라이언트 인증서 |
| `client_key` | **전통 RSA 포맷** — 4.4절 |
| `mqtt.host` | 비워두면 **요청의 `Host` 헤더**가 그대로 내려간다 |
| `mqtt.port` | 기본 8883 |
| `cameras` | **없을 수 있다** — 4.3절 |

### 4.3 `cameras` 는 없어도 성공이다

서버에 `/etc/adts/cameras.json` 이 없거나 JSON 파싱에 실패하면 **경고만 남기고 그 키를
빼고** 200 을 보낸다. 등록 자체를 실패시키면 카메라 설정이 준비되기 전에는 아무도 못
붙기 때문이다.

**클라이언트는 `cameras` 없음을 오류로 다루지 말 것.** MQTT 는 되고 영상만 안 나오는
상태이며, Qt 는 등록 완료 창에서 그 사실을 사용자에게 알린다. 사용자가 등록 화면에서
직접 넣은 카메라 정보가 **우선**이고 이 값은 폴백이다.

### 4.4 클라이언트 키는 전통 RSA 여야 한다

서버는 `<CN>-trad.key`(전통 RSA)를 내려준다. **PKCS#8 을 주면 안 된다.**

> Qt `QSslKey` 는 OpenSSL 3.x 기본인 PKCS#8 키를 `QSsl::Rsa` 로 읽으면 **null 을 반환하고
> 조용히 실패**한다. 예외도 로그도 없다. 증상은 "인증서 파일은 다 있는데 mTLS 만 안
> 붙음" 이라 원인을 찾기 어렵다.

서명에는 **`-extensions v3_client`** 가 들어가야 한다. 빠지면 브로커의 mTLS 핸드셰이크가
거부한다.

### 4.5 발급 측의 의무 — ACL 등록

발급만 하고 끝나면 안 된다. **브로커 ACL 에 그 CN 블록을 추가하고 reload 해야 한다.**

```
user qt-console-<라벨>
topic write adts/cmd/#
topic read  adts/state/#
topic read  adts/event/#
```

mosquitto 의 `user` 는 **정확 매칭이고 와일드카드가 없다.** 빠뜨리면 TLS 핸드셰이크는
성공하는데 구독·발행만 조용히 막힌다 — 인증서도 정상, 연결도 정상, 그런데 아무 메시지도
안 오간다. 지금은 발급 서비스가 자동으로 붙이고 `systemctl reload mosquitto` 를 부른다
(`restart` 가 아니다 — 붙어 있던 클라이언트가 전부 끊긴다).

권한 판정은 **Client ID 가 아니라 인증서 CN** 으로 이뤄진다(`use_identity_as_username
true`). Qt 는 동시 접속에서 서로 끊기지 않도록 `qt-console-<호스트명>-<난수>` 로 매번 다른
Client ID 를 쓰는데, 그래도 ACL 이 그대로 통하는 이유가 이것이다.

## 5. `GET /scans`

```json
{"scans":[{"name":"scan_20260821_143012.pcd","size":1843200,"mtime":1755760212}]}
```

- **경로는 주지 않는다.** 파일명·크기·수정시각만. 클라이언트는 파일명만 알면 되고 서버가
  디렉터리를 고정하고 있어 경로를 노출할 이유가 없다.
- `mtime` 은 유닉스 초.
- **한 번에 최대 500건.** 초과분은 조용히 잘린다.
- 목록에는 6절의 파일명 규칙을 통과한 `.pcd` 정규 파일만 들어간다.

## 6. `GET /scan/<파일명>`

응답 본문이 파일 그대로다. 파일명은 **세 겹**으로 검사한다.

| 겹 | 규칙 |
|---|---|
| ① | 길이 1~160, `..` 포함 불가, `/` 나 `%` 가 하나라도 있으면 거부 |
| ② | 문자는 영숫자와 `-` `_` `.` 만 |
| ③ | `.pcd` 확장자만 |

디렉터리는 서버의 `ADTS_SCAN_DIR` 로 고정이라 **경로 탈출이 성립할 수 없다.**

> `%` 를 디코드하지 않고 그냥 거부한다. 스캔 파일명에는 인코딩이 필요 없고, 디코더를
> 두면 그 자체가 새로운 우회 표면이 된다. **클라이언트는 파일명을 URL 인코딩하지 말 것.**

Qt 는 MQTT `state/scan` 으로 받은 경로에서 **파일명만 떼어** 이 경로로 요청한다. 데몬이
주는 경로는 RPi 기준이라 Qt 가 도는 PC 에는 존재하지 않기 때문이다.

## 7. 오류

| 코드 | 언제 |
|---|---|
| **400** | `Content-Length` 없음 / 본문 크기 이상 / 헤더 초과 / JSON 파싱 실패 / `token` 없음 / 파일명 규칙 위반 |
| **401** | 토큰이 유효하지 않거나 이미 사용됨 · `/scan` 계열에 검증된 클라이언트 인증서 없음 |
| **404** | 없는 경로 / 스캔 디렉터리 없음 / 그런 스캔 파일 없음 |
| **500** | 인증서 발급 실패 / ACL 갱신 실패 / 토큰 라벨이 CN 으로 쓸 수 없음 / 메모리·직렬화 실패 |

본문은 항상 `{"error":"사유"}` 다.

> **409 는 보내지 않는다.** 서버 코드에 409 를 내는 경로가 없다. 이전 문서 몇 곳에
> "401/409" 로 적혀 있었으나 오기다(2026-08-24 정정).

**401 은 "토큰이 틀렸다"와 "이미 썼다"를 구분해 주지 않는다.** 구분해 주면 공격자가 유효한
토큰 공간을 좁힐 수 있다. 서버 로그에는 둘 다 남는다.

## 8. 토큰

관리자가 만들어 사람 손으로 전달한다. 이 계약의 범위는 "Qt 가 받은 문자열을 그대로
`token` 에 넣는다" 까지다.

- **1회용.** 발급이 끝나면 서버가 토큰 파일에서 지운다.
- **만료가 없다.** 나눠주고 안 쓴 토큰은 회수 전까지 계속 유효하다.
- 라벨(=CN 접미사) 문자 집합은 영숫자와 `.` `_` `-`. 토큰을 **만들 때** 검사하므로
  클라이언트가 신경 쓸 일은 없다.

## 9. 성능·가용성 전제

발급 서비스는 **단일 스레드로 한 연결씩** 처리한다. 발급은 사람이 하루 몇 번 하는
작업이고, 토큰 파일과 ACL 파일을 동시에 건드릴 일이 없어 잠금 없이 안전하다.

대신 한 연결이 멈추면 **그동안 아무도 발급받지 못하고 스캔 다운로드도 막힌다.** 소켓에
**20초** 송수신 마감시간이 걸려 있어 최악의 정지 시간이 그만큼이다.

> 클라이언트는 여러 스캔 파일을 **병렬로 내려받지 말 것.** 서버가 순차 처리라 이득이 없고,
> 그동안 다른 사람의 등록이 막힌다.

## 10. 미결·주의

**① CRL 이 없다.** ACL 블록을 지우면 그 CN 으로 아무것도 못 하게 되지만, **인증서 자체는
여전히 유효해서 브로커 연결(TLS 핸드셰이크)은 된다.** 기기 분실 대응이 필요하면
`mosquitto.conf` 에 `crlfile` 을 걸어야 한다. Qt 의 "로그아웃" 은 로컬 파일을 지울 뿐이다.

**② 재발급은 이전 인증서를 폐기하지 않는다.** 같은 CN 으로 다시 발급하면 서버가 기존
파일을 지우고 새로 만들지만, 이미 나간 인증서는 암호학적으로 그대로 유효하다.

**③ `/scans`·`/scan` 실장비 왕복 검증이 안 됐다.** 재빌드·재기동 후 끝까지 확인한 적이
없다(RPi `84251db` 커밋 메모).

**④ 공용 CN `qt-console` 이 아직 ACL 에 남아 있다.** `gen-certs.sh` 전체 발급이 만드는
개발용 인증서다. 사람별 발급으로 완전히 전환하면 지워야 한다.
